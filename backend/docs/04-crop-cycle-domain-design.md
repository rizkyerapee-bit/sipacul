# Crop Cycle Domain Design

## 1. Document Purpose

This document defines the domain baseline for Sprint 15 of SiPacul.

The Crop Cycle module connects:

- organization;
- commodity;
- cultivation SOP;
- land;
- land plot;
- cultivation period;
- operational activities in Sprint 16;
- harvest and sales in Sprint 17;
- financial calculation and profit sharing in Sprint 18;
- land history and evaluation in Sprint 19.

The module must remain organization-scoped and suitable for a future
multi-tenant SaaS deployment.

## 2. Domain Language

The code-level aggregate name is `CropCycle`.

The user-facing Indonesian term is `Siklus Budidaya`.

A crop cycle represents one cultivation period for one commodity on one
land plot.

Examples:

- paddy cultivation on Plot A during the first planting season of 2027;
- chili cultivation on Plot B from nursery preparation until harvest;
- maize cultivation managed under one investment and operational period.

## 3. Aggregate Boundary

### 3.1 Aggregate root

`CropCycle` is an aggregate root.

The aggregate owns its lifecycle state and cultivation-period rules.

### 3.2 External references

The aggregate references existing organization-scoped entities:

- `Organization`;
- `Commodity`;
- `CultivationSop`, optional;
- `Land`;
- `LandPlot`.

These referenced entities remain separate aggregates.

### 3.3 Future child records

The following records are not part of Sprint 15:

- cultivation activities;
- material and labor usage;
- equipment usage;
- harvest records;
- sales;
- expenses;
- investor capital;
- partner capital;
- profit-sharing settlement;
- evaluation findings.

They will reference `CropCycleId` in later sprints.

## 4. Crop Cycle Properties

The initial aggregate should contain:

| Property | Type | Rule |
|---|---|---|
| `Id` | `Guid` | Generated by the domain |
| `OrganizationId` | `Guid` | Required and immutable |
| `Code` | `string` | Required, normalized uppercase, immutable |
| `Name` | `string` | Required |
| `CommodityId` | `Guid` | Required and immutable after creation |
| `CultivationSopId` | `Guid?` | Optional; editable only before start |
| `LandId` | `Guid` | Required and immutable |
| `LandPlotId` | `Guid` | Required and immutable |
| `PlantedArea` | `decimal` | Greater than zero |
| `AreaUnit` | `AreaUnit` | `SquareMeter` or `Hectare` |
| `PlannedStartDate` | `DateOnly` | Required |
| `ExpectedHarvestDate` | `DateOnly` | Required and after planned start |
| `ActualStartDate` | `DateOnly?` | Set when the cycle starts |
| `ActualHarvestDate` | `DateOnly?` | Set when the cycle completes |
| `Status` | `CropCycleStatus` | Controlled by lifecycle methods |
| `CancellationReason` | `string?` | Required only when cancelled |
| `Notes` | `string?` | Optional |
| audit properties | inherited | Follow the existing aggregate pattern |

The aggregate does not duplicate organization, commodity, land, plot, or
SOP names. Historical operational records will preserve the actual work
performed in later modules.

## 5. Crop Cycle Status

The first version uses four statuses:

```text
Planned
InProgress
Completed
Cancelled
```

### 5.1 Planned

The cycle has been registered and may still be edited.

No actual cultivation work has started.

### 5.2 InProgress

Cultivation has started.

The following identity fields are locked:

- organization;
- code;
- commodity;
- land;
- land plot;
- planted area and its unit;
- cultivation SOP.

Operational activities may be added in Sprint 16.

### 5.3 Completed

The cultivation period has ended.

The cycle is retained permanently for reporting, accounting, and land
history.

A completed cycle cannot be changed back to an earlier status.

### 5.4 Cancelled

The cultivation plan was stopped before completion.

A cancellation reason is mandatory.

A cancelled cycle remains available for audit and evaluation.

## 6. Lifecycle Transitions

Allowed transitions:

```text
Planned -> InProgress
Planned -> Cancelled
InProgress -> Completed
InProgress -> Cancelled
```

Disallowed transitions include:

```text
Completed -> any other status
Cancelled -> any other status
InProgress -> Planned
```

No reopen operation is included in the MVP.

Corrections to terminal records should later use an explicit audit or
administrative correction process rather than silently changing history.

## 7. Domain Methods

The aggregate should expose behavior-oriented methods.

### 7.1 `Create`

Creates a cycle in `Planned` status.

Validation includes:

- organization identifier is not empty;
- code is valid;
- name is not empty;
- commodity identifier is not empty;
- land identifier is not empty;
- land plot identifier is not empty;
- planted area is greater than zero;
- area unit is supported;
- expected harvest date is after planned start date;
- optional text values are normalized.

### 7.2 `UpdatePlan`

Allowed only while status is `Planned`.

Editable values:

- name;
- cultivation SOP;
- planted area;
- area unit;
- planned start date;
- expected harvest date;
- notes.

Immutable values:

- organization;
- code;
- commodity;
- land;
- land plot.

### 7.3 `Start`

Allowed only from `Planned`.

Requires:

- actual start date;
- actual start date must not be after expected harvest date.

Effects:

- sets `ActualStartDate`;
- changes status to `InProgress`;
- updates audit timestamp.

### 7.4 `Complete`

Allowed only from `InProgress`.

Requires:

- actual harvest date;
- actual harvest date must not be before actual start date.

Effects:

- sets `ActualHarvestDate`;
- changes status to `Completed`;
- updates audit timestamp.

The existence and validity of harvest records will be added in Sprint 17.

### 7.5 `Cancel`

Allowed from `Planned` or `InProgress`.

Requires a non-empty cancellation reason.

Effects:

- stores the normalized reason;
- changes status to `Cancelled`;
- updates audit timestamp.

### 7.6 `UpdateNotes`

Notes may be updated while status is `Planned` or `InProgress`.

Terminal cycles remain immutable in the MVP.

## 8. Code Rules

Crop-cycle codes follow the same normalization convention as existing
organization-scoped codes:

- trim whitespace;
- convert to uppercase;
- allow letters, numbers, hyphens, and underscores;
- reject unsupported characters;
- enforce a documented maximum length;
- unique within one organization.

Example codes:

```text
SC-PADI-2027-01
SC-CABAI-LHN01-2027
MT-2027-001
```

The same code may exist in different organizations.

## 9. Organization-Scoped Reference Rules

The Application layer must verify all references before creating or
updating a cycle.

### 9.1 Organization

The organization must exist and must not be deleted.

### 9.2 Commodity

The commodity must:

- belong to the same organization;
- exist;
- be active.

### 9.3 Land

The land must:

- belong to the same organization;
- exist;
- be active.

### 9.4 Land plot

The plot must:

- belong to the selected land;
- belong to the same organization;
- exist;
- be active.

### 9.5 Cultivation SOP

When supplied, the SOP must:

- belong to the same organization;
- exist;
- be active;
- use the same commodity as the crop cycle.

A cultivation SOP remains optional because a cultivation cycle may be
created before a formal SOP is available.

## 10. Area Rules

The domain validates that planted area is greater than zero.

The Application layer validates capacity because the aggregate does not
own the land plot.

Rules:

- convert planted area to square meters;
- planted area must not exceed the selected plot area;
- the area unit must use the existing `AreaUnit` enum;
- no automatic resizing of the plot is allowed;
- changing planted area is allowed only while `Planned`.

The first MVP allows one crop cycle to use part or all of one plot.

A single crop cycle cannot span multiple plots.

A multi-plot farming project can be represented by multiple crop cycles
and grouped later through an investment or project module.

## 11. Scheduling and Overlap Rules

The system must prevent conflicting cultivation periods on the same plot.

### 11.1 Planned overlap

Two non-cancelled cycles on the same plot may not have overlapping
planned date ranges.

The overlap formula is:

```text
existing.PlannedStartDate <= new.ExpectedHarvestDate
and
new.PlannedStartDate <= existing.ExpectedHarvestDate
```

Completed and cancelled cycles remain historical records but do not block
new cycles after their effective period.

### 11.2 Active-cycle rule

Only one `InProgress` crop cycle may exist on one plot at a time.

Starting a cycle must fail when another cycle on the same plot is already
`InProgress`.

### 11.3 Date adjustment

Changing planned dates while status is `Planned` must repeat the overlap
check.

## 12. Land and Plot Status Protection

After Crop Cycle application services exist:

- a land with a `Planned` or `InProgress` cycle cannot be deactivated;
- a plot with a `Planned` or `InProgress` cycle cannot be deactivated;
- a plot referenced by any historical cycle must not be physically
  deleted.

The current plot remove operation behaves as a hard removal from the
aggregate. Sprint 15 must therefore add a protection check before the
remove operation reaches the `Land` aggregate.

This preserves historical identity for completed and cancelled cycles.

## 13. Persistence Model

The planned table name is:

```text
CropCycles
```

Required database rules:

- primary key on `Id`;
- alternate key on `(OrganizationId, Id)`;
- unique index on `(OrganizationId, Code)`;
- index on `(OrganizationId, Status)`;
- index on `(OrganizationId, CommodityId)`;
- index on `(OrganizationId, LandId, LandPlotId)`;
- index on planned date range;
- restrictive foreign keys for historical safety;
- decimal precision consistent with Land and LandPlot area values;
- date columns mapped as PostgreSQL `date`.

Organization-scoped foreign keys should be used where the current
principal model supports them.

The LandPlot model may require an alternate key on:

```text
(OrganizationId, LandId, Id)
```

This allows the Crop Cycle foreign key to prove that the selected plot
belongs to the selected land and organization at database level.

## 14. Application Operations

The first Application service should provide:

```text
CreateAsync
GetAllAsync
GetByIdAsync
UpdatePlanAsync
StartAsync
CompleteAsync
CancelAsync
UpdateNotesAsync
```

Recommended list filters:

```text
status
commodityId
landId
landPlotId
plannedStartFrom
plannedStartTo
```

The first implementation may introduce filters incrementally, beginning
with status, commodity, and plot.

## 17. Explicit MVP Decisions

The following decisions are intentional:

1. One crop cycle belongs to exactly one plot.
2. One crop cycle has exactly one commodity.
3. A cultivation SOP is optional.
4. Crop-cycle identity cannot move to another plot after creation.
5. Terminal cycles are immutable.
6. Physical deletion of crop cycles is not included.
7. Physical deletion of referenced plots must be blocked.
8. Operational activities are deferred to Sprint 16.
9. Harvest and sales are deferred to Sprint 17.
10. Investment and profit sharing are deferred to Sprint 18.
11. Evaluation and historical insights are deferred to Sprint 19.
12. Authentication and tenant membership remain deferred to Sprint 20.

## 19. Acceptance Criteria

Sprint 15 is complete when:

- a valid crop cycle can be created for an active plot;
- invalid cross-organization references are rejected;
- planted area greater than the plot area is rejected;
- overlapping cycles on the same plot are rejected;
- lifecycle transitions follow the defined state machine;
- terminal cycles cannot be edited;
- active-cycle land and plot protections work;
- database constraints and indexes are verified;
- automated tests pass;
- end-to-end tests pass;
- test data is cleaned up;
- repository remains clean after verification.
